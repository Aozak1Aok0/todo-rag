# 双 Agent：检索回答 + 独立校验（2026-10-24）

> 代码：`rag/verify.py`（校验 Agent）· `rag/pipeline.py`（流水线）· `POST /rag-verify`
> 评测：`evals/verify_eval.py` · 结果：`evals/verify-{norevise,revise}-20261024.jsonl`

## 1. 设计

```
问题
  │
  ├─▶ 回答 Agent：retrieve(k=8) → 拼上下文 → 生成草稿（含引用）
  │
  ├─▶ 校验 Agent：只看「资料 + 问题 + 草稿」，逐条判断断言是否被支持
  │        └─ 输出 {"unsupported": [...], "verdict": "ok" | "revise"}
  │
  └─▶（可选）重写：把 unsupported 作为约束，让回答 Agent 重写 → 再校验一次
```

两个 Agent 共用一个检索结果，但**上下文不同**：回答 Agent 看的是拼接后的 prompt，校验 Agent 看的是"资料原文 + 草稿"，
避免"自己检查自己"。

- 校验口径偏严：资料没**直接**提到的细节一律算 unsupported（哪怕它可能是真的）。
- 端点：`POST /rag-verify {question, k?, max_revisions?}`。
- **默认 `max_revisions=0`（只报告，不自动重写）** —— 原因见下面的实测。

## 2. 实测（10 题，k=8）

| 配置 | 题均分 | 幻觉 | 输入 token/题 | 延迟/题 | 被标记 |
|---|---|---|---|---|---|
| RAG（当前语料，无校验） | 8.58 | 0 | ~1,450 | ~1.6s | — |
| RAG + 校验（只报告） | **8.92** | 0 | ~4,919（+239%） | ~2.9s | **6/10** |
| RAG + 校验 + 自动重写 | **6.92** | 0 | ~7,382（+409%） | ~4.3s | 5 次重写 |

> RAG 与「只报告」的答案相同（只多了一次校验调用），分数差异来自单次采样噪声；结论看**量级**，不要抠 0.3 分。

## 3. 关键发现：自动重写在这个语料上是**负收益**

自动重写把 5 道题改坏了：

| 题 | 草稿 | 重写后 | 原因 |
|---|---|---|---|
| Q3 初始数据 | 4/4（正确列出 3 条种子） | **0/4**（"无法确定"） | `store.py` 的 `init_db` 实现块没进 top-8，校验器判"3 条数据"无依据 → 重写把正确内容删了 |
| Q8 语料纠错 | 2/3（指出 `startsWith`） | **0/3**（"资料没说明对错"） | 正确拼写来自语言常识，不在语料里 → 被判 unsupported |
| Q4 422 解释 | 3/3 | 2/3 | 422 的通用解释不在语料里 → 被删 |
| Q1 路由清单 | 9/9 | 9/9（ sogar 更好：修正了计数） | 校验确实抓到了算术错误 |
| Q7 跨文件对比 | 3/4 | 3/4 | 误报（"node:sqlite 写法正确"被当成断言）但不影响 |

**根因：`unsupported` ≠ `wrong`。** 校验器只能判断"资料是否支持"，不能判断"命题是否为真"。当
(a) 检索漏了关键块，或 (b) 答案合理使用了资料外的通用知识时，重写会把正确答案改成"资料中没有"。

## 4. 只报告模式的误报率

只报告模式下 6/10 被标记，人工核对后**至少 3 条是误报**：

- Q6：「未发现明显拼写错误」是元评论，不是事实断言；
- Q7：「node:sqlite 导出 DatabaseSync」与官方一致，被判"资料未说明"；
- Q3：种子数据在语料里，只是没被检索进同一个上下文（k 不够 / 切块位置）。

所以校验结果适合做**信号**（人工或 UI 提示），不适合做**闸门**。

## 5. 结论与建议

1. `/rag-verify` 默认 `max_revisions=0`：返回 `verification` 字段，但不改答案；
2. 如果要开自动重写，至少满足：
   - 用更大的 k（10）并确认支持块确实在上下文里；
   - 只对**数值 / 实体 / 代码标识符**类断言触发重写，忽略元评论与措辞差异；
   - 答案里已经写「资料中没有」时不要重写；
3. 真正的收益方向不是"多一个 Agent"，而是**提高检索覆盖率**（按符号切块 / 更大的 k / 多查询召回）——
   本次实验里 Q1 的提升来自检索出的结构概览，不是校验本身。

## 6. 复现

```powershell
.\.venv\Scripts\python.exe evals\verify_eval.py --revisions 0   # 只报告
.\.venv\Scripts\python.exe evals\verify_eval.py --revisions 1   # 自动重写
```

结果文件：`evals/verify-norevise-20261024.jsonl`、`evals/verify-revise-20261024.jsonl`。

## 7. 追加：UI 展示 + 检索覆盖（2026-10-24 晚）

- React 前端改为调用 `POST /rag-verify`（`max_revisions=0`）：答案下方显示「校验：通过 / N 条未支持」，
  可展开查看断言与理由；**校验结果只展示，不改写答案**。
- 检索侧两处改进：
  - `store.py` 改为按符号切块（`init_db` / `list_todos` / `add_todo` / `remove_todo` 各自一块），
    解决「函数体被 30 行窗口切开」的问题；
  - 代码文件的结构概览附上函数 docstring 首句（例如 `init_db — 建表；只在空表时插种子，重复调用无副作用。`）。
- 指标变化（16 文件 / 63 块）：hit@1 **7/10**（原 6/10）、hit@3 10/10、MRR **0.85**（原 0.80）。
- 只报告模式复跑：7/10 被标记（校验偏严、误报多），但答案本身不受影响。
- 观察：`init_db` 的完整块在 k=8 下仍排第 12 位 —— **top-k 覆盖率**仍是主要瓶颈，不是校验器能解决的。
