# Q8 提示词 A/B（2026-10-20）

> 目的：Q8（`note/JS.txt` 里 `startWith()` 拼错）在「仅根据资料」的口径下只能拿 1/3 —— 资料没说"这是笔误"，模型就不敢断言。
> 验证：给提示词加一句"资料可能有误"，能不能救回这道题，以及会不会把幻觉放回来。

## 设置

| 项 | 值 |
|---|---|
| 条件 | 条件③ RAG，k=8，混合检索（当前索引 49 块，hit@3 = 10/10） |
| 变体 A | 原口径：「请仅根据上面的资料回答问题；资料里没有的，请明确说明「资料中没有」，不要编造。」 |
| 变体 B | A + 「资料本身可能有笔误或与公认事实冲突：遇到这种情况，请明确指出「资料中有误」，并给出正确说法。」 |
| 次数 | Q8 每变体 3 次；全 10 题各跑 2 次（查副作用） |

复现：`$env:RAG_PROMPT="B"; .\.venv\Scripts\python.exe evals\run_baseline.py --question Q8 --conditions rag`

## Q8 结果（3 次）

| 变体 | run1 | run2 | run3 | 均值 |
|---|---|---|---|---|
| A | 1/3 | 1/3 | 1/3 | **1.0 / 3** |
| B | 2/3 | 2/3 | 2/3 | **2.0 / 3** |

- A 三次都答对了 `startsWith`，但都补一句「资料里没有直接给出正确拼写」——**不敢把资料判成错的**。
- B 三次都明确说「资料中有误 / 拼写错了」，其中一次还解释了"判断前缀、返回 true/false"。
- 效果是**稳定的**：B 在 6 次运行（含上一轮）里都拿到了"指出笔误"这一点。

## 副作用：全 10 题跑两次，结果不一样

| 运行 | 变体 | 分数 | 幻觉 |
|---|---|---|---|
| 第 1 次 | A | 8.33 / 10 | 0 |
| 第 1 次 | B | **7.67 / 10** | **1**（Q5） |
| 第 2 次 | A | 8.33 / 10 | 0 |
| 第 2 次 | B | **8.67 / 10** | 0 |

第 1 次 B 在 **Q5（依赖版本）** 上翻车：

> 「需要指出：资料中有误——`openai==3.29.0` 这个版本号与公认事实不符，OpenAI Python SDK 目前并无 3.x 版本。」

而本机实际安装的就是 **3.29.0**（`pip show openai`）。它拿过时的世界知识去"纠正"语料 —— 标准幻觉。

第 2 次 B 没再犯（同一 prompt、temp=0）—— 又一次证明**单次运行不能下结论**（见 `comparison-v1-v2.md` 的非确定性实验）。

## 结论

1. **B 的收益稳定（Q8 +1 分），风险不稳定（2 次全量里 1 次出现假纠正）** → **不设为默认**。
2. Q8 的 1/3 不是 bug，是严格 grounding 的必然结果：判断"资料写错了"本来就超出语料。
3. 想救 Q8 又不放大幻觉，走更窄的变体 C：只允许纠「**代码标识符 / API 名称的拼写**」，不要泛化成"与公认事实冲突"（后者正是它去质疑 `openai==3.29.0` 的入口）。
4. 方法论：这种 A/B 至少要 **N=3 的全量跑** 才能判断，否则两次运行就能得出相反结论。

## 顺带修掉一个检索 bug

B 在 Q7 里指出「结构概览把 POST 处理函数标成了 `L40: function name()`」—— 一查是 `structure_outline` 把**缩进的** `const name = (...)` 当成了函数声明。已改为只取顶格代码，重建索引后概览只剩真实路由。

同时把「点名文件」的规则从"补进 top-k"改成"置顶"：命中率从 `hit@1 6/10 / hit@3 9/10 / MRR 0.77` 回到 **`hit@1 8/10 / hit@3 10/10 / MRR 0.90`**。

## 追加：变体 C（只纠「代码标识符 / API 名称」）

规则 C = A + 「如果资料中的代码标识符或 API 名称存在明显拼写错误（与该语言的标准库/官方 API 不一致），请指出并给出正确写法；**其它内容一律以资料为准，不要用资料之外的知识去否定资料**。」

### Q8（3 次）

| 变体 | run1 | run2 | run3 | 均值 |
|---|---|---|---|---|
| A | 1/3 | 1/3 | 1/3 | 1.0 |
| B | 2/3 | 2/3 | 2/3 | 2.0 |
| **C** | **2/3** | **2/3** | **2/3** | **2.0** |

C 的答案都会说「资料中写的是 startWith()，但标准应为 startsWith()」，并拿 `endsWith()` 的拼写作对照 —— 与 B 同样有效。

### 全 10 题（C 跑 2 次）

| 运行 | A | B | C |
|---|---|---|---|
| 第 1 次 | 8.33 / 0 幻觉 | 7.67 / **1 幻觉** | **8.67 / 0 幻觉** |
| 第 2 次 | 8.33 / 0 幻觉 | 8.67 / 0 幻觉 | **8.33 / 0 幻觉** |
| 第 3 次 | — | — | **8.67 / 0 幻觉** |
| 均值 | 8.33（2 次） | 8.17（2 次） | **8.56（3 次）** |

- C 三次都**没有**假纠正：Q5 老老实实列了 6 个包（包括 `openai==3.29.0`），不再质疑版本号。
- C 的 Q7 末尾还会主动写一句「资料中的标识符与标准库/框架用法一致，未发现明显拼写错误」—— 有点啰嗦，但无害。
- 代价：C 的第 2 次运行里 Q4 变保守了（不再解释 422 的通用含义，只说"资料没提"），少 0.33 分。属于提示词"以资料为准"的副作用，值得继续观察。

### 决定

**默认采用 C。** 理由：
1. Q8 从 1/3 稳定提升到 2/3（6 次运行一致）；
2. 三次全量都没有假纠正（0/3），风险明显低于 B（2 次里 1 次）；
3. 规则本身是有边界的（只允许纠标识符），不是无边界的"你可以质疑资料"。

已落地：`rag/prompt.py` 的 `DEFAULT_VARIANT="C"`（可用 `RAG_PROMPT=A|B|C` 覆盖），`evals/run_baseline.py` 默认也是 C；`/rag` 端点不需要改，它调用的是同一份 `build_rag_messages`。

⚠️ 注意：`:8000` 上那个后台服务是旧代码，**重启后才会用 C**。

样本量：C 跑了 3 次全量（8.67 / 8.33 / 8.67，均值 8.56），假纠正 0 次；Q8 单题 3/3 次都是 2/3。但单次波动 ±0.33，与 A 的总分差距仍在噪声范围内 —— 真正稳的是「Q8 能力」和「没有假纠正」，不是总分。
