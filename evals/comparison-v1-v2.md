# baseline v1 → v2 对比（2026-10-18）

> v1：`baseline-218e53a-20261016.jsonl`（eval v0.1，内存 list 版，20 行）
> v2：`baseline-dad0e13-20261018.jsonl`（eval v0.2，SQLite 版，20 行，30 s；分数已写入）
> 模型都 `deepseek-chat` / `temperature=0` / `max_tokens=1024`；条件均为 noctx + fullctx。
> v2 语料：15 个文件 / 23,291 字符（v1 是 21,834 —— 多出来的是 SQLite 代码）。

## 0. 一句话结论

**分数没变（1.00 vs 1.00；9.42 vs 9.42），但 v2 的 gold 才是对的。**

真正变化的不是代码让模型答得更好/更差，而是：**Q7、Q9 的判分锚点必须跟着代码改**。如果继续拿 v1 的 gold 去判 v2 的回答，这两题会被误判成 0 分 —— 那才是"改完代码分数暴跌"的假警报。

## 2. 重要发现：`temperature=0` 不等于可复现

v2 跑完后我发现 Q10/noctx 的回答和 v1 不一样（v1 笃定地说 `OPENAI_API_KEY`，v2 改成"配置项（如 LLM_MODEL）……以上为基于常见实现的概括"）。但 **Q10 的 prompt 一个字都没改**。

于是同一天、同一 prompt、同参数，连跑两次 Q10/noctx：

| 次数 | 回答长度 | 内容 |
|---|---|---|
| run 1 | 486 字 | 提到 `model` / `base_url` / `api_key`，还引用了 OpenAI SDK 的报错原文 |
| run 2 | 328 字 | 改成 `LLM_MODEL` / `LLM_BASE_URL` / `LLM_API_KEY`，并说"有默认值" |

**结论：这个 API 在 `temperature=0` 下仍不确定。** 影响：

- 单次 run 的"某题对/错"有抖动，**±1 题（±0.1~0.3 分）不能当信号**；
- v1→v2 里 Q10 从"幻觉"变"不幻觉"，**大概率是噪声，不是改进**；
- 以后比较 RAG 前后，要么 **N≥3 取平均**，要么把回答缓存下来对比同一份输出，别拿单次 run 下结论。

## 3. 给 RAG 评测的建议（改 `run_baseline.py` 之前先定）

1. **跑 N=3**：每题每条件 3 次，报告均值 + 最大最小（成本 ×3，v2 一次约 9 万 token，仍在几毛钱量级）。
2. **先固定"评分锚点版本"再比分数**：v2 已经做了（`eval_version: ["0.2"]` 写进 manifest）。
3. 若 API 支持 `seed`，可以试着传（OpenAI 兼容接口不一定实现；即便支持也只是"尽力"）。
4. **重点看粗指标**：`幻觉题数`、`Q9 是否拒答/纠正`、`Q7 是否两边都覆盖` —— 这些比 0.1 分的差异稳。
